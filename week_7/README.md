# RuleChat

**Chat with Enterprise Business Rules**

A conversational AI agent that lets business users, developers, and auditors query IBM ODM (Operational Decision Manager) rule repositories in natural language, with structured graph queries, semantic search, and interactive visualizations.

## 1. Project Overview

### 1.1 The Core Idea

RuleChat is a conversational AI application designed for IBM ODM (Operational Decision Manager) rule repositories. ODM is the dominant enterprise business rule management system used across insurance, banking, healthcare, and financial services. A typical ODM project contains hundreds of interconnected business rules — decision tables, business rule language (BRL) rules, rule flows — that govern automated decisions such as loan approvals, insurance premium calculations, eligibility determinations, fraud detection thresholds, and regulatory compliance checks.

The fundamental observation behind RuleChat is that **enterprise rule repositories are structurally rich but conversationally opaque**. Every rule has a precise, machine-readable definition. Every attribute has a typed schema. Every dependency is explicit. Yet none of this structure is accessible to the people who depend on these decisions every day — business analysts who need to understand how pricing rules work, compliance officers who need to verify regulatory requirements are met, product managers planning rule changes, and even rule developers themselves who spend hours manually tracing dependencies across hundreds of files.

RuleChat closes this gap by exposing the entire rule project through a chat interface. Behind the scenes, it constructs a complete dependency graph using NetworkX, indexes verbalized rule descriptions in a FAISS vector database via Cohere Embed v4, and orchestrates a Claude Sonnet 4.5 agent (via AWS Bedrock and Google ADK) with twelve specialized tools that can answer questions about rule logic, attribute lineage, dependency chains, and impact analysis. Users interact through a Streamlit web interface that supports natural language queries, interactive dependency visualizations, click-to-context exploration, and inline Mermaid diagrams generated by the agent itself.

### 1.2 The Problem It Addresses

Enterprise business rules are simultaneously the most important and the most opaque component of large software systems. They encode the institutional knowledge of how a business makes decisions — knowledge that took years to develop, frequently changes due to regulation or strategy, and must be auditable for compliance purposes. Despite this importance, the tooling for understanding them has remained largely unchanged for two decades.

Today, when a question arises about a specific rule — “Why was this customer denied?”, “What changes if we adjust the age threshold?”, “Where is the regulatory check for AML compliance?” — answering requires either deep technical expertise with ODM’s proprietary formats or a dedicated rules engineer’s time. The bottleneck is real: large enterprises commonly have a small team of two to five rules specialists supporting dozens of business analysts and compliance officers. Every question becomes a ticket. Every ticket takes hours. Every change requires extensive impact analysis that is performed manually by tracing XOM paths through rule files.

Three specific pain points emerge from this gap:

**Discovery is hard.** Finding the rules that govern a specific scenario requires knowing the project’s organization — package names, file structures, rule naming conventions. A new team member might spend weeks just learning where things live. Even experienced engineers waste time hunting for the right rule when a question arises.

**Dependency tracing is manual.** ODM rules have complex relationships: Rule A produces attribute X, which Rule B consumes alongside attribute Y produced by Rule C. Understanding the full execution flow for any non-trivial decision requires walking the dependency graph by hand, opening multiple files, and reading proprietary expression syntax.

**Impact analysis is expensive.** Before changing a rule, engineers must answer: what depends on this rule? If the risk-scoring rule changes, which downstream rules are affected, and what business outcomes might shift? Without automated tooling, this question takes hours per rule and often results in surprises during testing.

The cumulative cost is substantial. Across a Fortune 500 company with hundreds of rules across multiple business lines, the manual overhead of rule comprehension and dependency tracing can easily consume one to two full-time engineering positions, while still creating delays for business teams waiting for answers.

### 1.3 The Opportunity

Three technological shifts have converged to make a conversational solution feasible for the first time:

**LLM tool-calling has matured.** Claude Sonnet 4.5, accessible through AWS Bedrock, reliably selects the correct tool from a set of twelve and chains multiple tool calls to answer complex questions. Tool-calling reliability has crossed the threshold where it can be trusted with structured queries against a real domain.

**Graph-augmented retrieval is well understood.** The pattern of combining vector similarity search with graph traversal — finding relevant starting points semantically, then expanding through structural relationships — produces precise, traceable results for queries over interconnected data.

**Enterprise data already has structure.** Unlike unstructured document retrieval (PDFs, web pages), ODM rules are already well-typed and relationally rich. The work of parsing and structuring is already done by the rule engine itself. RuleChat just needs to lift that structure into a queryable graph.

The opportunity is to capture this convergence in a focused application: a chat interface that knows how to navigate a specific kind of structured enterprise data. The result is faster decisions, lower engineering overhead, broader access to institutional knowledge, and an audit trail of every question asked and answered.

## 2. Use Case and Workflow

### 2.1 Primary Users and Their Needs

RuleChat is designed for four user populations, each with distinct needs but a shared frustration with current tooling.

**Business analysts** need to understand what rules govern specific business processes. They ask questions like “What determines whether a customer qualifies for a premium discount?” or “Which rules check the customer’s credit history?” They speak in business terminology, not technical terms. They need answers that explain logic in plain English, not snippets of proprietary rule syntax.

**Rule developers** need to perform dependency analysis and impact assessment. They ask questions like “If I change the age threshold in the risk-scoring rule, what downstream rules are affected?” or “Show me the full execution chain leading to the final decision.” They are comfortable with technical detail but need it surfaced quickly, not through manual file traversal.

**Audit and compliance officers** need to verify that specific regulatory requirements are implemented as rules and understand which rules might be affected if regulations change. They ask questions like “Find rules that implement AML checks” or “What rules apply to customers in the EU?” They need traceability — they must be able to show auditors exactly which rules govern a decision and how those rules relate.

**Product managers and strategists** need to understand the rules landscape before proposing changes. They ask questions like “What rules currently differentiate premium-tier customers?” or “How is eligibility determined?” They need quick orientation without becoming experts in the rule format.

### 2.2 The Workflow Without AI

To illustrate the current pain, consider a representative scenario. A business analyst at an insurance company wants to understand why a particular customer’s quoted premium was higher than expected. The current workflow looks like this:

1. The analyst examines the quote and sees the final premium amount but no breakdown of how it was calculated.
1. They submit a ticket to the rules engineering team asking for an explanation.
1. An engineer opens the rule project in IBM ODM Decision Center or an IDE.
1. The engineer locates the final pricing rule, opens its file, and identifies the input attributes used in the premium calculation.
1. For each input attribute, the engineer searches the project to find which rules produce it. This requires understanding the XOM (eXecutable Object Model) naming convention and may involve searching across dozens of files.
1. For each producing rule, the engineer recursively traces its inputs, building up a mental model of the dependency chain.
1. The engineer cross-references decision-table rows to identify which specific row applied to this customer based on their attribute values.
1. The engineer writes up a plain-English summary for the analyst, often using business terminology that doesn’t directly appear in the rule files.
1. The analyst reads the summary, asks one or two follow-up questions, and the cycle repeats.

Total elapsed time: anywhere from two to six hours of engineering effort, plus another day of waiting time for the analyst. This scenario plays out dozens of times per week in a typical enterprise rules organization.

### 2.3 The Workflow With RuleChat

The same scenario, with RuleChat:

1. The analyst opens the RuleChat web interface.
1. They type: *“What rules determine the premium rate for a 35-year-old EU customer with high credit?”*
1. RuleChat’s agent calls `get_rules_producing_attribute` to find which rules produce the `premiumRate` attribute. It identifies the Premium Calculation rule as the producer.
1. The agent calls `get_dependent_rules` to find Premium Calculation’s upstream dependencies, identifying Risk Scoring and Eligibility Check.
1. The agent calls `get_rule_hierarchy` to expand the full dependency tree.
1. The agent recognizes the question is suitable for a visual diagram and includes an inline Mermaid flowchart showing the dependency chain.
1. The agent responds in natural language using business terminology, explains how each rule contributes to the premium, and offers to drill into any specific rule.
1. The analyst clicks a node in the diagram to ask a follow-up about Risk Scoring specifically.

Total elapsed time: under thirty seconds. No engineering ticket required.

### 2.4 How AI Improves the Workflow

The AI layer provides three categories of value beyond what a traditional search interface or rule browser could offer:

**Intent translation.** A user might say “what affects pricing?”, “show me pricing rules”, “find rules that calculate premiums”, or “where is the premium logic?” These are all semantically equivalent questions that would each require different filters in a traditional UI. The LLM agent recognizes them as the same intent and selects the appropriate tool combination. This dramatically reduces the learning curve.

**Contextual synthesis.** A traditional tool would return a list of rules and let the user interpret them. The agent synthesizes results from multiple tool calls into a coherent narrative that uses the user’s vocabulary, explains relationships in business terms, and proactively offers relevant next steps. The synthesis layer is what makes the output usable by non-technical users.

**Adaptive depth.** Different questions require different depths of investigation. “What does rule X do?” needs a quick summary. “Compare rule X and rule Y” requires fetching details for both rules and explaining differences. “Find rules that handle edge cases for non-standard customers” requires multi-step LLM-guided navigation through the rule hierarchy. The agent decides how deep to go based on the question, whereas a static interface would either over-fetch (wasting context window and time) or under-fetch (forcing the user to ask many follow-up questions).

Without the AI layer, users would need to learn the schema of twelve tools, the XOM naming convention, the graph traversal patterns, and the rule format itself. With it, they just need to ask in plain language.

## 3. AI Features to Be Implemented

This section explains both *what* will be implemented and *why* each feature is essential for this specific use case.

### 3.1 Prompt Engineering

The core of RuleChat’s behavior lives in the agent instruction — a carefully constructed system prompt that governs tool selection, response formatting, context handling, error recovery, and visualization decisions. This is not a single static prompt; it is a structured document with sections covering distinct concerns:

- **Role definition**: establishes the agent as an expert on IBM ODM business rules.
- **Tool selection strategy**: maps user question patterns to specific tool sequences. For example, specific rule queries trigger `get_rule_by_name` first, while category queries (“find rules that handle X”) trigger `navigate_rule_hierarchy`.
- **Context tag handling**: defines how to interpret four types of UI-injected context tags. When the user selects a rule in the sidebar dropdown, the message is prepended with `[Context: Rule = 'X']`. When they click a node in the lineage visualization, multiple `[Selected: ...]` tags appear. The agent must respect these without re-asking the user what they mean.
- **Error recovery flows**: scripts the agent’s behavior when a tool returns an error. For “rule not found” errors, the agent must call `list_all_rules` to find similar names and retry rather than giving up.
- **Visualization rules**: defines when to include Mermaid diagrams inline versus when to escalate to the full interactive `generate_lineage_graph` tool. Includes strict syntax constraints (quoted node labels, no parentheses, max 20 nodes).
- **Output formatting**: specifies that responses use verbalized rule names with XOM paths only on first mention, never show raw JSON to the user, and never leak implementation details (NetworkX, FAISS, embedding, Bedrock).

The justification for treating prompt engineering as a first-class engineering discipline is that this single string determines every user-visible agent behavior. A small change to tool selection guidance can dramatically alter which questions get answered correctly. A missing constraint can cause the agent to leak technical jargon to non-technical users. Without rigorous prompt engineering, the entire application falls apart.

### 3.2 Structured Outputs

RuleChat enforces structured outputs at three distinct layers, each with its own validation strategy:

**Tool responses.** Every one of the twelve tools returns a JSON string with a consistent shape. The agent receives typed data it can reason about, not free-form text. Error responses follow a standard schema (`{"error": "...", "suggestion": "..."}`) so the agent knows how to recover. Empty results are explicit dictionaries with explanatory messages, never null or empty arrays without context.

**Navigation prompts.** The `navigate_rule_hierarchy` tool makes internal LLM calls at three levels — package selection, rule selection, and row selection. Each of these calls uses Claude with `temperature=0` and explicit JSON schemas. The orchestrator validates responses against the schemas, strips markdown code fences if present, and fails closed if the JSON is malformed. This ensures the multi-step navigation produces traceable, debuggable output.

**Mermaid diagrams.** When the agent decides to include a visual diagram in its response, the syntax follows strict rules: all node labels must be quoted (`A["Premium Calculation"]` not `A[Premium Calculation]`), edge labels must be quoted (`-->|"risk score"|`), parentheses are forbidden in labels (they conflict with Mermaid syntax for rounded nodes), and diagrams are capped at 20 nodes to maintain readability. The Streamlit rendering layer splits responses at Mermaid boundaries and renders each segment separately, since `st.markdown` only renders Mermaid when the block is the sole content of the call.

The justification is reliability. LLMs are known to drift in their output formats over long conversations. By enforcing structure at each layer and validating before proceeding, RuleChat eliminates a class of failures that would otherwise manifest as broken visualizations, parsing errors, or hallucinated tool results.

### 3.3 Retrieval-Augmented Generation and Vector Databases

A typical ODM project at scale contains so many rules and attributes that even a focused subset exceeds 1.5 million tokens — far beyond any context window. RAG is not an optimization here; it is the only feasible architecture.

The retrieval pipeline works as follows:

**Verbalization.** Each rule, attribute, dependency edge, and decision-table row is converted into a natural language sentence by a `Verbalizer` module. For example, a rule node becomes: *“Rule ‘Premium Calculation’ is a decision_table that checks customer age (com.example.Customer.age) and customer region (com.example.Customer.region), and sets premium rate (com.example.Policy.premiumRate). Inputs: customer age, customer region. Outputs: premium rate.”* Both verbalized names (for business users) and XOM paths (for technical users) appear in every sentence, making the retrieval index searchable by either vocabulary.

**Embedding.** Sentences are embedded using Cohere Embed v4 (model `cohere.embed-v4:0`) via AWS Bedrock, producing 1024-dimensional vectors. Cohere uses an asymmetric encoding scheme: documents are embedded with `input_type="search_document"` during indexing, and queries are embedded with `input_type="search_query"` at retrieval time. Mismatching these silently degrades quality, so RuleChat’s embedding wrapper raises an error if `input_type` is not explicitly specified.

**Storage.** Embeddings are stored in a FAISS `IndexFlatIP` (inner product over L2-normalized vectors, which equals cosine similarity). At the expected scale of tens of thousands of sentences, exact search is sub-millisecond and outperforms approximate methods like HNSW in both speed and accuracy. The index is persisted to disk alongside the rule project’s content hash, so subsequent startups skip re-embedding unless rules have changed.

**Retrieval with graph expansion.** The `search_rules` tool implements the GraphRAG pattern: a vector similarity search identifies the top-k most relevant sentences, the corresponding NetworkX nodes are extracted, and a BFS expansion in both directions (outgoing and incoming edges) gathers surrounding context. The expanded subgraph’s sentences are deduplicated and ranked, with original semantic matches appearing first.

The justification is that semantic search alone misses structurally relevant information, while structural traversal alone misses semantically relevant rules whose names don’t keyword-match the query. Combining both produces precise, contextually rich retrieval.

### 3.4 Evaluation Techniques

RuleChat treats agent quality as a measurable property, not a hoped-for outcome. The evaluation strategy is built around an autoresearch loop adapted from Andrej Karpathy’s pattern: generate, measure, keep, mutate, repeat.

The loop operates on a fixed test set of representative user questions paired with binary success criteria. Criteria fall into three categories:

- **Deterministic tool-call checks** verify that the agent calls the correct tool first for a given question. These are computed by inspecting the agent’s tool call history, with no LLM judgment involved.
- **Regex pattern checks** verify response formatting rules — no raw JSON, no implementation leakage, correct Mermaid syntax, presence of required tags.
- **LLM-judge checks** evaluate subjective qualities like response clarity or completeness. The judge is a fresh Claude instance with no knowledge of what was mutated, ensuring blind evaluation.

The loop applies one of six mutation operators (add constraint, add negative example, restructure, tighten language, remove bloat, add counterexample) to the target asset (agent instruction, verbalizer template, tool docstrings), runs the test set against the mutated version, computes a score, and either keeps the change (if it improves by a confidence margin) or reverts. The loop continues until three consecutive perfect scores, a maximum run count, or five stale runs trigger a plateau breaker that rewrites the target from scratch.

The justification is that prompt engineering without measurement is just guessing. Autoresearch turns the prompt tuning process into a flywheel: every improvement is measurable, every regression is caught, every mutation operator’s effectiveness is tracked over time. This becomes especially important as RuleChat scales to handle more rule projects with diverse vocabularies.

### 3.5 Observability and Monitoring

Every agent decision in RuleChat is logged to a structured event stream. The observability plan is detailed in Section 7, but the core principle is auditability: enterprise users need to know not just what the agent answered, but exactly how it arrived at that answer.

The observability stack captures:

- **Tool-call traces**: every tool invocation with its arguments, return value, and timing.
- **Retrieval scores**: FAISS similarity scores for every semantic search query, monitored for distribution drift.
- **Navigation paths**: for `navigate_rule_hierarchy`, the full multi-step path including which packages and rules were considered at each level.
- **Autoresearch history**: every mutation, score delta, and keep/revert decision from the evaluation loop.
- **User interaction patterns**: which tools are used most often, which questions cause errors, which lineage graphs are explored.
- **Error surface monitoring**: distinct error categories (tool-not-found, rule-not-found, max-tool-calls-exceeded, navigation-budget-exceeded) with separate dashboards.

The justification is that enterprise AI applications must be auditable. When a compliance officer asks the agent about a regulatory rule, the resulting answer may inform a business decision. The full chain of evidence — which tools were called, which rules were retrieved, what the LLM saw at each step — must be reconstructable.

## 4. Technical Approach

### 4.1 System Architecture

RuleChat follows a strict layered architecture where each layer has a single responsibility and depends only on the layer below it. This separation makes the system testable, debuggable, and replaceable component by component.

```
┌──────────────────────────────────────────────────────────────────┐
│                       USER INTERFACE LAYER                       │
│  Streamlit chat · sidebar dropdowns · interactive lineage graphs │
│  context injection · Mermaid rendering · message history         │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│                          AGENT LAYER                             │
│  Google ADK · Claude Sonnet 4.5 via Bedrock (LiteLLM wrapper)    │
│  agent instruction · tool selection · response synthesis         │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│                        RETRIEVAL LAYER                           │
│  9 deterministic graph tools · search_rules (semantic + BFS)     │
│  navigate_rule_hierarchy (multi-step LLM) · generate_lineage     │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│                          DATA LAYER                              │
│  NetworkX DiGraph · FAISS IndexFlatIP · Cohere Embed v4          │
│  ODM rule JSON files (single source of truth)                    │
└──────────────────────────────────────────────────────────────────┘
```

Data flows strictly downward at startup (rule files are parsed into the graph and indexed) and strictly upward at query time (user question becomes tool calls become retrieved data becomes synthesized response).

### 4.2 Data Layer in Detail

The data layer’s primary artifact is a **NetworkX DiGraph** built from parsed ODM rule JSON files. The graph contains two types of nodes:

**Rule nodes** carry the complete rule definition: rule name, type (decision table or business rule language), preconditions, condition definitions, action definitions, decision-table rows with their nested conditions and actions, input and output attribute lists, and function definitions. The node ID is the rule’s unique identifier.

**Attribute nodes** are unique per `xomElementName` across the entire project. They carry the verbalized name, data type, the list of rules that produce this attribute (`producedBy`), the list of rules that consume it (`consumedBy`), and an `attributeCategory` of either `independent` (not produced by any rule in the project, must be provided as external input) or `dependent` (produced by at least one rule). The XOM element name serves as the node ID.

Three types of edges connect these nodes:

- **PRODUCES** edges connect a rule node to each attribute it outputs.
- **CONSUMED_BY** edges connect each input attribute to the rule that consumes it.
- **DEPENDS_ON** edges connect a rule to another rule when the first consumes an attribute the second produces. These are derived during graph construction by cross-referencing all input and output attributes. The edge carries a `sharedAttributes` property listing the specific XOM element names that create the dependency.

The dependency derivation step is critical and deserves emphasis. Without these derived edges, the graph would only contain rule-to-attribute and attribute-to-rule relationships, requiring two-hop traversal to find which rules depend on which. By materializing the rule-to-rule edges during construction, subsequent queries become O(1) lookups.

Preconditions add another layer of complexity. Many ODM rules have preconditions that reference additional attributes not appearing in the main condition or action lists. The graph builder explicitly inspects `preconditions.referencedAttributes` and treats those references the same as input attributes when deriving DEPENDS_ON edges. This ensures the graph captures the full transitive dependency surface.

The graph is built once at startup from the rule JSON files, which are the single source of truth. If rule files change, the entire graph is rebuilt — there is no incremental update mechanism. This is a deliberate choice: rebuilding takes seconds, and the resulting graph is guaranteed consistent with the source.

### 4.3 Vector Index Architecture

Parallel to the graph, RuleChat maintains a FAISS vector index built from verbalized sentences. The verbalization process produces four sentence categories per rule project:

- **Rule sentences**: one per rule, summarizing what the rule checks and sets.
- **Attribute sentences**: one per unique XOM element name.
- **Dependency sentences**: one per DEPENDS_ON edge, explaining which shared attributes create the dependency.
- **Rule-row sentences**: one per row of a decision table, capturing specific conditions and actions.

All four categories live in the same FAISS index, distinguishable by their entry type. This enables both broad queries (“what rules handle pricing?”) and narrow queries (“what happens when customer age is over 25 and region is EU?”) to be answered by the same retrieval mechanism — the row-level sentences naturally surface for specific-condition queries because their embeddings are closer to those queries than the rule-level sentences.

The choice of Cohere Embed v4 over alternatives (OpenAI’s text-embedding-3, open-source models like BGE) was driven by three factors: native AWS Bedrock availability (matching the existing Claude inference stack), strong performance on enterprise/structured text per benchmarks, and the asymmetric encoding model that explicitly distinguishes search documents from search queries. The 1024-dimensional output is a balance between retrieval quality and index size; the model also supports 256, 512, and 1536 dimensions.

The choice of FAISS `IndexFlatIP` over approximate methods (HNSW, IVF) is unambiguous at this scale. Exact inner product search on tens of thousands of normalized vectors completes in sub-millisecond time. Approximate methods would trade accuracy for speed in a regime where there is no speed problem to solve. The recommendation to use HNSW only emerges above ten million vectors, which RuleChat will not reach until it indexes a hundred separate rule projects in a single deployment.

The index is persisted to disk along with a hash of the rule JSON files. On startup, RuleChat compares the current hash to the stored hash and skips re-embedding (which involves Cohere API calls and takes seconds to minutes) if nothing has changed.

### 4.4 Retrieval Layer: Twelve Tools

The agent has access to twelve tools, each a Python function with a clear docstring that Google ADK exposes to Claude as the tool description. Tool selection guidance is encoded in the docstrings themselves.

Nine tools are **deterministic graph queries** that perform direct lookups against the NetworkX graph:

1. `list_all_rules()` — returns all rule names and types.
1. `get_rule_by_name(rule_name)` — returns full rule details.
1. `get_input_attributes(rule_name)` — returns inputs enriched with category and producer info.
1. `get_output_attributes(rule_name)` — returns outputs.
1. `get_dependent_rules(rule_name)` — returns upstream dependencies (rules that must execute before this one).
1. `get_downstream_rules(rule_name)` — returns rules that depend on this one (for impact analysis).
1. `get_rule_hierarchy(rule_name, depth)` — performs BFS traversal and returns a layered dependency tree.
1. `get_independent_attributes(rule_name)` — returns input attributes that are not produced by any other rule.
1. `get_rules_producing_attribute(attribute_name)` — searches for rules by attribute (verbalized or XOM name).

One tool is **semantic search**: `search_rules(query)` calls the vector index’s `search_and_expand` method, returning relevant rules and their surrounding subgraph context.

One tool is **multi-step LLM-guided navigation**: `navigate_rule_hierarchy(query, ...)` is for category-style queries where neither deterministic lookup nor pure semantic search works well. It makes two to four internal LLM calls to navigate the rule hierarchy from packages down to specific rules and rows, with each navigation step producing JSON-schema-validated output. It is slower and more expensive than the other tools and is reserved for queries like “find rules that implement regulatory compliance” or “find exception-handling rules for non-standard customers.”

One tool is **visualization**: `generate_lineage_graph(rule_name, depth, direction, include_attributes)` returns a renderer-agnostic graph data structure that the Streamlit layer renders as an interactive visualization.

The justification for this tool split — deterministic versus semantic versus navigation versus visualization — is that user questions fall into distinct categories that benefit from different retrieval approaches. Specific rule queries should be O(1) lookups, not vector searches. Vague queries need semantic matching. Category queries need multi-step reasoning. Visualization requests need a different output modality. By exposing all four as distinct tools and letting the agent choose, RuleChat avoids the failure modes of any single approach.

### 4.5 Agent Layer

The agent is a Google ADK `LlmAgent` configured with Claude Sonnet 4.5 via LiteLLM and AWS Bedrock. The model string is `bedrock/us.anthropic.claude-sonnet-4-5-20250514-v1:0`. 

The agent’s instruction is a single comprehensive string covering all the prompt engineering concerns enumerated in Section 3.1. It is treated as the single most important artifact in the system because it determines every agent behavior. The instruction is optimized using the autoresearch evaluation loop described in Section 3.4.

Session management uses ADK’s `InMemorySessionService`. Each browser tab or user gets a unique session ID. Conversation history is maintained within a session, so users can ask follow-up questions like “what about its dependencies?” after asking about a specific rule, and the agent remembers what “it” refers to.

### 4.6 User Interface Layer

The Streamlit application provides the user-facing surface. Key components:

**Chat interface.** Standard Streamlit chat elements (`st.chat_message`, `st.chat_input`) with message history stored in `st.session_state.messages`. A critical implementation detail: agent responses containing inline Mermaid diagrams must be split at Mermaid block boundaries and rendered with separate `st.markdown` calls, because Streamlit only renders Mermaid when a code block is the sole content of a markdown call.

**Sidebar dropdowns.** Three optional dropdowns let the user select a specific rule, attribute, or tool. Selections are converted to context tags (`[Context: Rule = 'X']`, `[Context: Attribute = 'Y' (xom)]`, `[Suggested Tool: Z]`) that get prepended to the next message. The dropdowns are entirely optional — users can ask freeform questions without selecting anything.

**Lineage visualization.** When the agent calls `generate_lineage_graph`, the Streamlit app receives renderer-agnostic graph data and renders it using `streamlit-agraph` as the primary renderer with Pyvis as a fallback. Streamlit-agraph supports click-to-context — clicking a node in the graph adds it to a selected-nodes list (with duplicate detection and a five-node maximum) which gets injected as `[Selected: ...]` context in the next message.

**Interactive controls.** A “Clear Chat” button creates a new session ID while preserving the graph and index caches. A “Visualization Settings” expander controls lineage depth, direction, and renderer preference.

Streamlit’s caching primitives are used carefully. The graph and vector index are loaded once via `@st.cache_resource` and shared across users. The ADK runner and session service are per-user and are NOT cached. Numpy arrays, FAISS indexes, and streamlit-agraph Node/Edge/Config objects are never stored in session state — they don’t survive serialization across reruns. Only plain Python dicts (graph_data) are stored, and renderer-specific objects are rebuilt on every render.

## 5. Example Prompts and Expected Outputs

This section documents representative user interactions to illustrate the range of behaviors RuleChat supports.

### 5.1 Example 1: Specific Rule Inquiry

**User prompt:**

> “What does the Premium Calculation rule do?”

**Expected agent behavior:**
The agent recognizes that the user mentioned a specific rule by name and calls `get_rule_by_name("Premium Calculation")` as its first action. The tool returns the rule’s full details including type (decision_table), conditions, actions, and decision-table rows.

**Expected response:**

> Premium Calculation is a decision-table rule with seven rows. It checks the customer’s age, region, and risk score, then sets the premium rate based on the matching row. Inputs include customer age (com.example.Customer.age), customer region (com.example.Customer.region), and risk score (com.example.Policy.riskScore). The rule outputs the premium rate (com.example.Policy.premiumRate) and a discount factor. The decision table has separate rows for different combinations — for example, customers under 25 in the US get the standard rate with no discount, while customers over 35 with low risk get a 15% discount. Want me to show the full decision table or explain a specific row?

The response uses verbalized names, includes XOM paths on first mention only, suggests follow-ups, and never shows raw JSON.

### 5.2 Example 2: Dependency Inquiry with Visualization

**User prompt:**

> “Which rules feed into Premium Calculation, and what attributes do they share?”

**Expected agent behavior:**
The agent recognizes this as a dependency question with a visualization opportunity. It calls `get_dependent_rules("Premium Calculation")` to find upstream dependencies. Seeing that the question is about relationships with shared attributes, the agent decides to include an inline Mermaid diagram.

**Expected response:**

> Premium Calculation depends on two upstream rules. Here’s how they connect:
> 
> ```mermaid
> graph TD
>     A["Risk Scoring"] -->|"risk score, risk category"| C["Premium Calculation"]
>     B["Eligibility Check"] -->|"eligible flag"| C
>     style C fill:#FF6B6B,stroke:#333,stroke-width:2px,color:#fff
> ```
> 
> Risk Scoring produces the risk score and risk category, which Premium Calculation uses to determine the rate. Eligibility Check produces the eligible flag — if the customer isn’t eligible, Premium Calculation does not execute. Both upstream rules must produce their outputs before Premium Calculation can run.
> 
> Want me to drill into Risk Scoring or Eligibility Check?

The Mermaid block is rendered as an interactive diagram inline. Node labels are quoted, the focal rule is highlighted, and edge labels list the shared attributes.

### 5.3 Example 3: Impact Analysis

**User prompt:**

> “If we change the age threshold in Risk Scoring, which rules are affected?”

**Expected agent behavior:**
The agent identifies this as an impact analysis question. It calls `get_downstream_rules("Risk Scoring")` to find rules that depend on Risk Scoring’s outputs. For deeper analysis, it may recursively call `get_downstream_rules` on each affected rule.

**Expected response:**

> A change to Risk Scoring’s age threshold would propagate to three downstream rules.
> 
> ```mermaid
> graph TD
>     A["Risk Scoring"] -->|"risk score"| B["Premium Calculation"]
>     A -->|"risk category"| C["Underwriting Decision"]
>     B -->|"premium rate"| D["Final Quote"]
>     C -->|"underwriting result"| D
>     style A fill:#FF6B6B,stroke:#333,stroke-width:2px,color:#fff
>     style D fill:#FFD93D,stroke:#333
> ```
> 
> Directly affected: Premium Calculation (consumes risk score) and Underwriting Decision (consumes risk category). Both feed into Final Quote, so the change cascades to that rule as well — Final Quote will produce a different output for customers whose age now falls into a different risk band.
> 
> The age threshold change has the potential to affect any customer near the current boundary. I’d recommend running test cases at the old and new threshold values across all four downstream rules before deployment.

The agent proactively suggests testing strategy, demonstrating contextual synthesis beyond just listing affected rules.

### 5.4 Example 4: Category Query Requiring Navigation

**User prompt:**

> “Find rules that handle edge cases for non-standard customers in the EU market.”

**Expected agent behavior:**
This is a category query — the user describes a kind of rule rather than naming one. Semantic search alone might return rules whose names contain “EU” or “non-standard” but miss structurally relevant rules. The agent calls `navigate_rule_hierarchy("edge cases for non-standard customers in EU market")` instead.

The tool executes three internal LLM-guided navigation steps. Step 1 lists all rule packages with summaries and asks the LLM to select the most likely ones (`customer_validation` and `exception_handling`). Step 2 lists rules within those packages and selects three candidates: `NonStandardCustomerCheck`, `RegionalEligibilityException`, and `EUAgeBoundaryHandler`. Step 3 navigates into the decision-table rows of each candidate to identify rows matching the EU + non-standard criteria.

**Expected response:**

> I navigated your rule project to find edge-case handling for non-standard EU customers. Here’s what I found:
> 
> I first explored two packages: customer_validation and exception_handling. Within those, three rules look most relevant:
> 
> - **NonStandardCustomerCheck** — has a specific row that triggers when customer type is ‘non_standard’ AND region is in the EU set. The row sets exception_flag to true and routes to manual review.
> - **RegionalEligibilityException** — handles eligibility for customers whose region requires special treatment. EU rows apply when GDPR consent is missing.
> - **EUAgeBoundaryHandler** — addresses age threshold differences for EU jurisdictions where the standard 25-year threshold doesn’t apply.
> 
> All three are decision-table rules with multiple rows covering specific EU sub-cases. Want me to dive into any of these?

The response narrates the navigation path so the user understands why each candidate was selected, and offers drill-down.

### 5.5 Example 5: Error Recovery

**User prompt:**

> “Tell me about rule ‘PremiumCalc’.”

**Expected agent behavior:**
The agent calls `get_rule_by_name("PremiumCalc")`. The tool returns an error because no rule by that exact name exists. The agent’s instruction includes a scripted error recovery flow: on “rule not found” errors, call `list_all_rules` to find similar names.

The agent calls `list_all_rules`, scans the result, finds “Premium Calculation” as a likely match, and retries.

**Expected response:**

> I couldn’t find a rule called ‘PremiumCalc’ exactly, but there’s a rule named ‘Premium Calculation’ that looks like what you’re asking about. Want me to describe that one?

The agent fails gracefully, suggests a correction, and asks for confirmation before proceeding. It does not show the raw error or fabricate information.

## 6. Evaluation Strategy

### 6.1 What We Measure

RuleChat’s effectiveness is measured along four dimensions, each with its own test set and metrics:

**Tool selection accuracy.** Does the agent call the correct tool for a given question type? This is measured deterministically by inspecting the agent’s tool call history. A test case consists of a user question paired with the expected first tool call. Pass/fail is binary. This metric directly reflects the agent instruction’s quality.

**Retrieval precision.** When the agent calls `search_rules`, does FAISS return the expected rule in the top-1 position? Top-3? Top-5? Test cases pair user queries with the rule ID that should be retrieved. This measures verbalization quality and embedding model performance.

**Response compliance.** Does the agent’s response follow all formatting rules? Specific checks include: no raw JSON visible to the user, no leakage of implementation details (NetworkX, FAISS, Cohere, Bedrock), correct Mermaid syntax (quoted labels, no parentheses), verbalized names used (not rule IDs), XOM paths only on first mention. These are deterministic regex-based checks.

**Subjective quality.** Is the response clear, accurate, and helpful? This requires an LLM judge — a separate Claude instance with no knowledge of what was being evaluated, given only the user question, the agent response, and a binary criterion. The judge returns yes/no for each criterion.

### 6.2 The Autoresearch Loop

The evaluation strategy is operationalized through an autoresearch loop. The loop operates on one target at a time — agent instruction, verbalizer template, or tool docstrings — and runs the following cycle:

1. **Baseline.** Run the current version of the target against the fixed test set. Record the score.
1. **Mutate.** Apply one of six mutation operators to generate a new candidate version. Operators rotate to ensure coverage: add constraint, add negative example, restructure, tighten language, remove bloat, add counterexample.
1. **Evaluate.** Run the test set against the candidate version. Compute the score. Crucially, the LLM judge runs in a fresh conversation with no knowledge of the mutation — this prevents the judge from grading charitably toward changes it made.
1. **Keep or revert.** Compare the candidate score to the current best. If the improvement exceeds the confidence margin (typically 2 points), keep the candidate. Otherwise revert. Log which mutation operator was used and the resulting score delta.

The loop continues until one of three stopping conditions: three consecutive perfect scores, a maximum run count, or five stale runs (no improvements). When stale runs are detected, a plateau breaker discards the current target and rewrites it from scratch using accumulated failure patterns.

### 6.3 Test Set Construction

Test sets are version-controlled JSON files committed to the repository. Each test case is structured as:

```json
{
  "id": "tc_042",
  "category": "specific_rule",
  "question": "What are the inputs of Premium Calculation?",
  "criteria": [
    {"type": "tool_call_check", "expected_tool": "get_input_attributes"},
    {"type": "regex_check", "pattern": "verbalizedName"},
    {"type": "llm_judge", "criterion": "Response explains what each input is used for"}
  ]
}
```

Test sets cover all behaviors: specific rule queries, vague exploratory queries, category queries, visualization requests, comparison questions, error recovery, context-tag handling, multi-turn follow-ups, and edge cases like rules with no dependencies or attributes with no producers.

For tool selection optimization, the test set heavily weights confused tool pairs — `search_rules` vs `navigate_rule_hierarchy`, `get_dependent_rules` vs `get_downstream_rules`, text vs visual responses. These are the failure modes most likely to confuse the agent and most worth catching.

### 6.4 What “Done” Means

A target is considered optimized when it achieves three consecutive perfect or near-perfect scores against the fixed test set. At that point, the loop halts and the final version is saved.

Optimization is not a one-time event. As new rule projects are onboarded, new question patterns emerge, and the agent instruction is re-optimized against an expanded test set. Autoresearch becomes a continuous quality assurance mechanism that runs whenever significant changes are made.

## 7. Observability Plan

### 7.1 Logging Strategy

Every event in RuleChat is logged to a structured JSONL event stream — append-only, easy to grep, easy to feed into analysis tools. Six event categories are tracked:

**Tool-call events.** Every tool invocation logs the tool name, arguments, return value (truncated for large responses), execution time, and success/error status. These logs make every agent decision auditable and reproducible.

**Retrieval events.** Every `search_rules` invocation logs the query, the embedded query vector hash, the top-k results with their similarity scores, and the BFS expansion details. Score distributions are monitored over time — a sudden drop in average top-1 score indicates either verbalization quality degrading or user query patterns shifting.

**Navigation events.** Every `navigate_rule_hierarchy` invocation logs the three-step navigation path: which packages were considered and selected, which rules within those packages were selected, and which decision-table rows were identified as matches. Each step’s LLM reasoning is captured.

**Autoresearch events.** Every mutation, score, and keep/revert decision from the evaluation loop is logged to `.autoresearch/results.jsonl`. This creates an audit trail of how the agent’s instruction evolved over time.

**User interaction events.** UI-level events: which dropdowns were used, which lineage graphs were generated, which nodes were clicked, how many context tags were injected. These reveal usage patterns and inform UX improvements.

**Error events.** Distinct categories: tool-not-found errors, rule-not-found errors, max-tool-call-exceeded errors, navigation-budget-exceeded errors, Mermaid render failures, Cohere API failures, Bedrock rate limits. Each category is tracked separately because they require different remediation.

### 7.2 Monitoring Dashboards

The proposal includes a dashboard with the following views:

**Agent health view.** Tool-call success rates, average response latency, error rate per error category. This is the operational view — does the system work?

**Retrieval quality view.** Score distributions for `search_rules` over time, navigation success rates for `navigate_rule_hierarchy`, top-1 retrieval accuracy on test set. This is the AI-quality view — does the AI work well?

**Usage view.** Which tools get called most often, which question types are most common, what is the distribution of conversation lengths. This is the product view — what are users doing?

**Autoresearch view.** Score trajectories for each target, mutation operator effectiveness, time-since-last-improvement. This is the meta view — is the system getting better over time?

### 7.3 Alerting

Alerts are configured for operational issues that require immediate attention:

- Tool-call error rate exceeds 5% over a rolling 5-minute window.
- Retrieval top-1 accuracy on the canonical test set drops below 80%.
- Agent response time p95 exceeds 30 seconds.
- Bedrock or Cohere API errors persist for more than 60 seconds.
- Autoresearch loop fails to improve for five consecutive runs (triggers plateau breaker).

Alerts are intentionally narrow — false positives erode trust. Only conditions that indicate real degradation trigger alerts.
